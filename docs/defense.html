🛡️ Zero-Trust Security

Distributed Attack Defense & Protection

Real-time voting applications face adversarial vectors: bot ballot stuffing, volumetric DDoS, 6-character short-code brute force, and runaway cloud billing ("Denial of Wallet"). Here is our 5-Layer Defense-in-Depth Architecture.

🌐

Layer 1: Edge & Volumetric DDoS Mitigation (L3/L4 & L7)

Infrastructure Ingestion Protection
Absorbs Gbps Floods

Volumetric attacks (SYN floods, UDP amplification, HTTP request storms) are absorbed at the global Anycast edge network (Google Cloud Armor / Cloudflare Edge / AWS Shield) before reaching the app's compute instances or triggering billing meters.

🔥 Firebase: Handled automatically by Google Global Anycast Edge & Google Cloud Armor.
⚡ Supabase / Self-Hosted: Put Cloudflare Enterprise / Free Reverse Proxy in front of API & WebSocket ports.
📱

Layer 2: Cryptographic Device Attestation (Anti-Bot & Anti-Emulator)

Hardware Proof-of-Origin
Blocks Script Farms

To stop attackers writing simple Python curl scripts or launching thousands of headless emulators, LivePulse integrates Hardware Device Attestation (Play Integrity / Firebase App Check). Every vote payload includes a cryptographically signed token proving it originated from a genuine, untampered physical Android device.

// Android Client Play Integrity Attestation
val appCheckToken = FirebaseAppCheck.getInstance().getToken(false).await()
// Token contains hardware cryptographic signature validated by backend servers
🔑

Layer 3: Sybil & Short-Code Brute Force Prevention

Rate Limiting & Idempotency Keys
1 Vote Per Person

6-character join codes (e.g., SOC5V5) have 36^6 = ~2.17 billion combinations. To prevent automated scraping or guessing:

  • 🔒 Sliding Window Rate-Limits: Max 10 short-code lookups per minute per IP / Device Token.
  • 🆔 Compound Idempotency Keys: Votes use document key ${pollId}_${userId}. 10,000 duplicated requests overwrite the exact same record rather than inflating vote counts.
🔒

Layer 4: Database-Level Row Security & Schema Validation

Server-Side Zero Trust ACL
Immutable Rules

Even if an attacker bypasses the client APK, the cloud database rejects unauthorized modifications. Only the poll creator can delete or close a poll; voters can only append their own vote document.

💰

Layer 5: Financial Defense & "Denial of Wallet" Hard Caps

Budget Shields & Circuit Breakers
$0 Shock Protection

Malicious actors often attempt "Denial of Wallet" attacks by generating billions of reads to trigger surprise cloud bills. LivePulse mitigates this with Room SQLite local read caching, client-side debounce(300ms), and GCP / Supabase spend caps.

firestore.rules FIREBASE SECURITY 
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /polls/{pollId} {
      allow read: if true;
      allow create: if request.auth != null;
      allow update, delete: if request.auth != null 
        && request.auth.uid == resource.data.creatorId;

      match /votes/{voteId} {
        allow read: if true;
        allow write: if request.auth != null 
          && request.auth.uid == request.resource.data.voterId;
      }
    }
  }
}
schema.sql (Postgres RLS) SUPABASE / POSTGRES 
ALTER TABLE votes ENABLE ROW LEVEL SECURITY;

-- 1. Public can read votes
CREATE POLICY "Public votes are readable" 
ON votes FOR SELECT USING (true);

-- 2. Voters can only insert/update their own vote
CREATE POLICY "Users can only cast their own vote" 
ON votes FOR INSERT 
WITH CHECK (auth.uid() = voter_id);

-- 3. Composite unique constraint prevents Sybil ballot stuffing
ALTER TABLE votes ADD CONSTRAINT unique_voter_per_poll 
UNIQUE (poll_id, voter_id);
